# 多网卡宿主机下的组播通信问题总结

## 1. 问题背景

同一台宿主机存在多个网络接口：

```text
宿主机
├── 网卡1：192.243.121.2
└── 网卡2：192.243.121.45
```

两个容器均使用 `host` 网络模式，因此容器直接使用宿主机的网络栈。

通信方式为 UDP Multicast，例如：

```text
239.x.x.x:xxxx
```

发送端从 `192.243.121.2` 对应的网卡发送组播。

---

## 2. 出现的问题

### 同一宿主机

发送端：

```text
192.243.121.2
      ↓
   239.x.x.x
```

接收端如果使用：

```text
192.243.121.45
```

对应的网络接口加入组播，则**无法正常收到**。

但是如果接收端改为使用：

```text
192.243.121.2
```

对应的网络接口加入组播，则可以正常收到。

宿主机通过抓包可以确认，组播报文实际上已经产生并进入宿主机网络栈。

---

## 3. 跨宿主机时没有这个问题

如果发送端和接收端位于不同宿主机：

```text
Host A                         Host B
192.243.121.2                  192.243.121.45
     │                              ↑
     │        Multicast             │
     └──────────→ 网络 ─────────────┘
```

此时接收端使用 `192.243.121.45` 对应的网卡加入组播，可以正常收到。

---

## 4. 根本原因

问题的核心在于：

> **同一宿主机多网卡场景下，本地生成的组播报文不会默认跨不同网络接口进行本地组播转发。**

也就是说：

```text
同一宿主机：

eth0 / .2
    │
    │ 本地生成 Multicast
    ↓
 239.x.x.x
    │
    ✕
    │
eth1 / .45
```

`.2` 网卡产生的组播，并不会默认像经过外部网络一样，再转发到 `.45` 网卡对应的组播接收路径。

因此：

```text
发送接口 = .2
接收接口 = .45
```

这种**同一宿主机跨网卡的组播通信**就会出现接收不到的问题。

---

## 5. 为什么跨宿主机正常？

跨宿主机时，组播报文是真正经过网络传输的：

```text
Host A
  .2
   │
   ↓
网络接口
   │
   ↓
交换机 / 网络
   │
   ↓
Host B
  .45
   │
   ↓
组播接收程序
```

此时 `.45` 网卡是真正从网络上**收到组播报文**，因此可以正常进行 multicast membership 和 UDP 数据投递。

所以：

> **跨宿主机属于正常的网络组播流程，而同一宿主机的 `.2 → .45` 属于本地不同网络接口之间的组播转发问题。**

---

## 6. 当前解决方案

接收端不再使用 `.45` 作为组播接收接口，而是使用与发送端一致的 `.2`：

```text
发送：
192.243.121.2
      ↓
   239.x.x.x
      ↓
接收：
192.243.121.2
```

这样发送和接收使用同一个 multicast interface：

```text
发送接口 = .2
接收接口 = .2
```

从而绕过：

```text
.2 → .45
```

之间的本地跨网卡组播转发问题。

---

## 7. 本质总结

整个问题可以概括为：

```text
┌──────────────────────────────────────────────┐
│              同一宿主机                      │
│                                              │
│  .2 ───────→ Multicast                      │
│   │                                            │
│   │       ❌ 默认不会跨网卡本地转发           │
│   ↓                                            │
│  .45 ──────→ 接收不到                         │
│                                              │
└──────────────────────────────────────────────┘
```

而跨宿主机：

```text
┌──────────────┐          ┌──────────────┐
│   Host A     │          │   Host B     │
│     .2       │          │     .45      │
│      │       │          │       ↑      │
└──────┼───────┘          └───────┼───────┘
       │                          │
       └────── Multicast ─────────┘
                  │
              实际网络
                  │
                 ✅
```
本質區別其實就一句話：

> **同一宿主機是「Linux 內核內部跨網卡」；跨宿主機是「真正經過網絡傳輸」。**

可以看成：

### 同一宿主機

```text
eth0 (.2)
   │
   │ 本機產生組播
   ↓
Linux Kernel
   │
   X  ← 不會默認跨到另一張網卡
   │
eth1 (.45)
```

`.2` 發出的組播已經在**本機內核裡**處理了，並不會因為目的地址是組播，就自動從 `.45` 再「繞出去」。

---

### 跨宿主機

```text
Host A                         Host B
eth0 (.2)                      eth1 (.45)
   │                               ↑
   ↓                               │
網卡 → 交換機/網絡 → 網卡
       ↑
   真正的網絡傳輸
```

這時 `.45` 是**真正從網絡上收到一個 multicast frame**，所以 `.45` 上的 multicast membership 可以正常匹配並交給程序。

---

### 所以最核心的區別

| 情況    | `.2 → .45` 的本質 | 結果       |
| ----- | -------------- | -------- |
| 同一宿主機 | Linux 本機不同網卡之間 | 不默認跨接口轉發 |
| 跨宿主機  | 真正經過網絡設備傳輸     | 正常接收     |

因此你的解決方法：

```text
接收接口從 .45 改成 .2
```

本質上不是「修好了組播」。

而是：

> **不再要求 Linux 做本機 `.2 → .45` 的跨網卡組播轉發，而是讓接收端直接加入 `.2` 這個組播接口。**

這就是你這個問題最核心的區別。


### 结论

> **这是同一宿主机多网卡环境下的本地组播跨接口转发问题，而不是 Docker `host` 网络模式或 UDP 本身的问题。当前通过让接收端使用与发送端相同的 `.2` 组播接口，避免跨 `.2 → .45` 网卡转发，从而解决接收问题；跨宿主机时由于组播经过实际网络传输，因此不存在该问题。**
