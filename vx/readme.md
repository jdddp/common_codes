# 微信小程序设备借还管理系统

## 1. 项目概述

### 1.1 项目名称

微信小程序设备借还管理系统

### 1.2 项目目的

本系统用于企业、实验室、项目组等内部场景，对设备的**分类、数量、用户、借用、归还以及历史记录**进行统一管理。

系统不以传统 ERP 或完整资产管理系统为目标，而是重点解决以下问题：

* 当前有哪些设备类型
* 每种设备共有多少台
* 当前已经借出多少
* 当前还有多少可用
* 哪些用户正在借用设备
* 用户什么时候借用、什么时候归还
* 管理员能够管理设备和用户
* 用户能够查看自己的借用情况
* 用户能够主动归还设备
* 管理员能够查询完整的借还历史

### 1.3 系统定位

系统采用：

```text
微信小程序
    │
    ▼
微信云开发
    ├── 云函数
    └── 云数据库
```

不部署独立服务器。

不需要：

* FastAPI
* Flask
* Django
* Nginx
* 公网 IP
* 端口映射
* HTTPS 服务器
* 自建数据库服务器

# 4. 登录与认证设计

## 4.1 登录方式

系统采用：

```text
手机号 + 密码
```

手机号作为用户登录账号。

例如：

```text
手机号：138XXXXXXXX
密码：********
```

管理员同样使用管理员绑定的默认手机号作为登录账号。

---

## 4.2 为什么不使用 OpenID 作为业务账号

微信 OpenID 可以用于识别微信用户，但本系统的业务需求明确要求：

> 用户使用手机号和密码登录。

因此业务层不直接依赖 OpenID 登录。

微信小程序主要作为系统客户端。

认证逻辑由云函数完成：

```text
小程序
   │
   │ phone + password
   ▼
auth 云函数
   │
   ├── 查询用户
   ├── 检查账号状态
   ├── 验证密码
   └── 创建登录会话
```

# 5. 密码安全设计

## 5.1 不保存明文密码

数据库中不能保存：

```text
password: 123456
```

而应该保存：

```text
passwordHash
```

例如：

```text
$2b$12$xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

推荐使用：

```text
bcrypt
```

或者其他成熟的密码哈希算法。

---

## 5.2 前端禁止保存管理员密码

不能在小程序代码中写：

```javascript
const adminPassword = "123456";
```

也不能：

```javascript
if (password === "123456") {
    // 管理员
}
```

管理员账号的初始化应该在云端完成。

---

# 6. 密码修改功能

系统支持两种密码操作。

## 6.1 用户修改自己的密码

普通用户和管理员都可以修改自己的密码。

流程：

```text
旧密码
   ↓
新密码
   ↓
确认新密码
   ↓
提交
```

云函数执行：

```text
1. 验证当前登录用户
2. 查询用户
3. 验证旧密码
4. 检查新密码
5. 生成新的 passwordHash
6. 更新数据库
7. 使旧 Session 失效
```

---

## 6.2 管理员修改其他用户密码

管理员可以直接重置其他用户密码。

流程：

```text
管理员
  ↓
用户管理
  ↓
选择用户
  ↓
修改密码
  ↓
输入新密码
  ↓
确认新密码
```

不需要输入旧密码。

管理员也不能查看原密码。

---

## 6.3 密码权限矩阵

| 操作       | 普通用户 | 管理员 |
| -------- | ---: | --: |
| 登录       |    ✅ |   ✅ |
| 修改自己的密码  |    ✅ |   ✅ |
| 查看自己的密码  |    ❌ |   ❌ |
| 查看其他人密码  |    ❌ |   ❌ |
| 修改其他用户密码 |    ❌ |   ✅ |
| 重置其他用户密码 |    ❌ |   ✅ |

# 7. Session 设计

登录成功以后不能每次请求都传手机号和密码。

建议：

```text
登录
 ↓
生成 token
 ↓
小程序保存 token
 ↓
后续请求携带 token
```

例如：

```text
login
    ↓
token
    ↓
getCurrentUser
borrowDevice
returnDevice
listRecords
...
```

---

## 7.1 passwordVersion

为了让管理员重置密码后，用户原来的登录状态失效，可以在用户表增加：

```text
passwordVersion
```

例如：

```text
passwordVersion: 1
```

用户修改密码：

```text
passwordVersion: 2
```

Token 中记录：

```text
userId
passwordVersion
```

服务器验证：

```text
token.passwordVersion
        ==
user.passwordVersion
```

如果不一致：

```text
登录状态失效
```

这样管理员重置用户密码后，该用户之前的 Session 会自动失效。

# 10. 用户状态

用户状态：

```text

```

正常用户，可以登录和借用设备。

## disabled

禁用以后：

* 不能登录
* 不能借用设备

# 13. 设备库存设计

本系统第一版不追踪单台设备。

例如：

```text
HDY-V3
总数 20
```

不记录：

```text
HDY-V3-001
HDY-V3-002
HDY-V3-003
...
```

也不要求：

* SN
* 序列号
* MAC 地址
* 二维码
* RFID

---

## 13.1 库存概念

系统需要展示：

```text
总数量
已借数量
可用数量
```

逻辑关系：

```text
可用数量 = 总数量 - 当前未归还数量
```

例如：

```text
总数量 = 20

A 借 5
B 借 3

已借 = 8

可用 = 20 - 8 = 12
```

---

# 14. 设备数量修改

管理员可以修改：

```text
总数量
```

但是不能修改成小于当前已经借出的数量。

例如：

```text
总数量：20
已借：15
```

管理员最多只能改成：

```text
20 → 15
```

不能：

```text
20 → 14
```

否则会出现：

```text
总数量 < 已借数量
```

造成库存逻辑错误。

---

# 20. 借用不能相信前端数据

前端可能发送：

```javascript
{
    deviceTypeId: "xxx",
    quantity: 5
}
```

但是不能发送：

```javascript
{
    userId: "张三"
}
```

然后云函数直接相信。

正确做法：

```text
Token
 ↓
服务器解析 Token
 ↓
得到 userId
 ↓
使用服务器得到的 userId 创建记录
```

也就是说：

```text
userId 永远由服务端确定。
```

---

# 21. 并发借用问题

这是库存系统非常重要的一点。

假设：

```text
HDY-V3
总数 = 10
已借 = 8
可用 = 2
```

此时：

```text
用户 A 借 2
用户 B 借 2
```

如果两个请求同时：

```text
读取可用数量 = 2
```

然后都判断成功，就可能导致：

```text
实际借出 4
总库存只有 2
```

这是错误的。

因此借用操作必须考虑并发。

---

# 22. 推荐的库存一致性方案

借用操作应该使用：

```text
云数据库事务
```

或者其他具有原子性的库存更新机制。

核心思想：

```text
开始事务
   ↓
读取设备库存状态
   ↓
检查可用数量
   ↓
检查通过
   ↓
创建借用记录
   ↓
更新库存状态
   ↓
提交事务
```

任何一步失败：

```text
回滚
```

```text
        ↓
```

# 41. 权限控制

权限控制必须放在云函数。

不能只依赖：

```javascript

    显示管理按钮
}
```

因为隐藏按钮不等于安全。

攻击者仍然可以直接调用云函数。

正确方式：

```text
小程序
 ↓
调用云函数
 ↓
验证 Token
 ↓
获取当前用户
 ↓
判断 role
 ↓
执行操作
```

# 50. 数据一致性要求




# 65. 安全设计原则

系统必须遵守以下原则：

## 原则 1

密码永远不保存明文。

## 原则 2

前端不保存管理员密码。

## 原则 3

权限必须在云函数验证。

## 原则 4

不能相信前端传入的 userId。

## 原则 5

普通用户只能操作自己的借用记录。

## 原则 6

管理员重置密码后让旧登录状态失效。

## 原则 7

历史数据尽量不删除。

## 原则 8

库存修改必须保证并发一致性。

```text
用户
分类
设备类型
借用记录

```

核心关系：

```text
用户
 ↓
借用记录
 ↓
设备类型
 ↓
归还记录
```

库存：

```text
设备总数
    -
所有未归还数量
    =
当前可用数量
```

权限：

```text
admin
 ├── 用户管理
 ├── 设备管理
 ├── 全部记录
 └── 自己的密码

user
 ├── 查看设备
 ├── 借用
 ├── 归还
 ├── 自己的记录
 └── 自己的密码
```

# 80. 开发原则

整个项目开发过程中遵循：

```text
前端负责展示
        +
云函数负责业务
        +
数据库负责数据
        +
云函数负责权限
```

尤其是：

```text
不要相信前端传来的权限
不要相信前端传来的 userId
不要在前端保存密码
不要在数据库保存明文密码
不要使用非原子方式修改库存
不要删除有历史记录的数据
```
